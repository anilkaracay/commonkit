# PROFILES — the 12 scenarios as asset profiles

Each file in `profiles/` is a JSON `Profile` (CONTRACT_SPEC §2.1) plus a non-chain `meta` block used by the web app, the bridge and the agent. Amounts below are in NEAR for readability; files store yocto strings. Values are demo values; thresholds marked *(demo)* are lowered for the simulated demo (see notes). The JSON files are the source of truth; if this table and a file disagree, the file wins and this table is fixed.

Upkeep rules (D-017) are written as `Kind: rule_id (trigger) → rights [+ reimbursable max]`. "test" means `requires_verification_test: true`. Triggers: **Metric** (telemetry delta since the last reward ≥ threshold), **Schedule** (`every_hours` since the last reward), **Report** (`min_reports` active fault reports from distinct members). No profile uses `reward_cash` (all `0`); rewards are usage-right cards.

"Teach it" is not a rule kind: training goes through the commons credential flow (`propose_credential` → `approve_credential`, CONTRACT_SPEC §5), which mints the credential to the trainee and usage rights to the trainer. It applies to every asset with a `required_credential` (laser_cutter, gpu_server, tractor, emergency_generator).

Notes:
- v1 bills every asset per time slot; the "unit" label (kWh, km, cycle) is what telemetry measures and what the UI shows. Metered billing per unit is a documented next step — do not claim it.
- Reimbursement (Restock/Repair only): the worker claims a documented expense with a receipt hash at `submit_task`, capped by `reimbursable_max` (`E_EXPENSE_CAP`). It is paid from the asset's free float, never from deposits; above `council_threshold_cash` it needs a council second approval; above `auto_reward_cash_cap` it is paid only through a DAO proposal (`escalate(kind="reimbursement")`). See CONTRACT_SPEC §3.3. Every reimbursable max in the table is ≤ that profile's `auto_reward_cash_cap`.
- Gauges that go up and down (`temperature_c`, `fuel_level`) never go on chain raw: `report_telemetry` accepts only monotonic counters (CONTRACT_SPEC §2.4). The bridge derives counters from them per asset config `gauges` (D-410): `temp_high_samples` counts telemetry samples above the fridge limit (× `telemetry_interval_sec` ≈ time out of range), `fuel_used_dl` sums fuel-level decreases in decilitres. Metric triggers use only these derived names (BRIDGE_AND_ADAPTERS §4.6). A live temperature display reads the bridge, not the chain.
- **Demo overrides** (`meta.pilot_overrides`, rule_id → lowered value): printer_3d `nozzle_clean` 1 800 s and `filament_spool` 5 000 mm; laser_cutter `lens_clean` 600 s and `monthly_safety_check` 1 h. They are applied with a DAO `set_profile` proposal so the simulated demo can reach each rule within minutes, and the README states them with the tx link. D-018 also lowers fridge `weekly_clean` to 1 h by a `set_profile` proposal (`community_fridge.json` `meta.pilot_overrides`). Every override actually applied on testnet is listed with its proposal and tx in [evidence/demo-overrides.json](../evidence/demo-overrides.json). The other profiles have no overrides.
- **Status (D-022):** no hardware is used. The four testnet assets (`printer-01`, `laser-01`, `washer-01`, `fridge-01`) are **simulation**: printer and laser run through the real `moonraker` / `smart_plug` adapters against device emulators (BRIDGE_AND_ADAPTERS §4.7), washer and fridge through the simulator. The other eight are **profile example only**: each validates against `profiles/profile.schema.json` and has a simulator scenario, and nothing more is claimed. `meta.status` in each file says the same.
- Every profile has `storage_reserve` 7 NEAR (D-021) and `price_per_slot + deposit_trusted > 0` (D-020); the table omits `storage_reserve`.
- `meta` block (not on-chain): `{ display_name, community, icon, photo, status, scenario_story_en, scenario_story_tr, pilot_overrides, purchase_hints: [{rule_id, after_n, item, amount, receiver}] }`.
- A JSON schema (`profiles/profile.schema.json`) mirrors `validate_profile`; CI validates all 12 files (`scripts/validate-profiles.ts`, test `scripts/validate-profiles.test.ts`).
- `scenarios/<asset_type>.yaml` drives the simulator for every profile (format: D-401), so judges can run `./scripts/simulate.sh <asset_type>` for any of the 12 on a local sandbox (D-420). Every run is labelled simulation down to the chain (`simulated = 1` metric, D-401). Each of the 12 scenarios makes at least one rule of its profile due, so every upkeep kind above is exercised by at least one simulation.
